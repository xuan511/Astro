博客里有三处音乐入口：音乐房间的完整面板、首页的小卡片，以及可以收起的迷你播放器。它们看起来是三个播放器，实际播放声音的只有一个 `<audio>`。

这个约束让切歌、暂停和进度同步有了明确的归属。页面上的按钮负责表达操作，持久控制器负责改变同一份音频状态。

## 控件可以有多个，声音只有一个来源

如果每个页面都创建自己的音频实例，切页时就需要决定旧实例何时暂停、新实例从哪里恢复，以及两边的异步加载谁才有效。一次快速点击，便可能同时触发两次播放。

本站采用的关系更简单：

```text
首页音乐卡 ─────┐
音乐房间面板 ──┼── 持久播放器控制器 ── 一个 audio
迷你播放器 ────┘              │
                             └── 同步标题、进度与播放模式
```

歌曲清单位于 `src/data/music.json`。构建时校验曲目，页面输出控制钩子；浏览器脚本从持久根节点读取清单。内容加载和实际播放因此不需要引入额外的组件运行时。

## 站内导航要保留真实节点

本站使用 Astro 的 `ClientRouter` 进行客户端导航，并为播放器根节点设置匹配的持久化名称：

```astro
<section id="persistent-player" transition:persist="shijian-player">
  <audio id="journal-audio" preload="none"></audio>
</section>
```

这段代码只展示节点关系。实际项目还包含歌单、按钮、状态区和控制脚本。

Astro 的 `transition:persist` 可以在客户端切换页面时保留匹配的 HTML 元素，官方以持续播放媒体为例说明了这一机制。本站把它用于音频节点，两端页面都需要输出同一个持久区域。[Astro 状态保持文档](https://docs.astro.build/en/guides/view-transitions/#maintaining-state)

新页面上的进度条和按钮仍然是新节点，所以控制器需要在 `astro:page-load` 后重新取得这些控件。保留下来的是播放实例，页面中的所有 DOM 并不会一起永久保留。

## 播放状态以音频本身为准

按下按钮之后，音频可能还在加载，也可能被浏览器拒绝播放。界面不能一收到点击就认定“已经播放”。

本站分别处理等待、播放、暂停和失败：播放按钮可以取消等待；发生媒体错误时显示原因，再按播放允许重试。快速切歌时，用递增的请求标记区分新旧操作，旧请求的结果不能覆盖最新曲目。

进度也来自音频的实际时间。拖动时可以先预览目标位置，松手后再定位，避免每移动一点都要求浏览器重新寻找音频数据。

这些处理让状态变化与实际媒体事件保持一致。唱片的旋转同样跟随播放状态，暂停后停住；系统要求减少动态效果时关闭旋转。

## 保存位置，不等于自动恢复声音

本地偏好保存歌曲 ID、位置、音量和模式。它解决的是“下次从哪里继续”，没有改变浏览器的播放授权规则。

几种情况需要分别理解：

| 操作 | 预期行为 |
| --- | --- |
| 正常站内客户端导航 | 尽量保留当前音频实例和播放 |
| 收起迷你播放器 | 只改变控件外观，音频继续 |
| 刷新、跨站跳转或新开标签 | 文档重建，不能保证声音延续 |
| 下一次手动播放 | 根据有效偏好恢复曲目与位置 |

如果保存的曲目已从清单移除，恢复逻辑会清空旧曲目的位置，保留有效音量和模式。这样不会把一首已经删除的歌的进度，误用到另一首歌上。

## 验证要观察连续的过程

连续播放不能只看一个暂停图标。检查时，先手动播放，再从音乐页进入文章和首页，观察音频实例标记是否相同、时间是否继续推进，以及页面内是否始终只有一个 `<audio>`。

之后再验证暂停、切歌、拖动、模式切换和刷新。刷新后的停止是浏览器生命周期的一部分，应与站内导航的异常中断分别记录。

下一次给页面增加播放入口，只需接入现有控制器。让状态只有一个明确的所有者，通常比事后同步多个播放器更容易维护。
